# Contributing

Thanks for looking. Bug reports, physics corrections and new machine topologies are
all welcome — this is a small project and there is no process to speak of.

## Getting set up

```bash
bun install     # bun.lock is the lockfile; please don't introduce npm/yarn/pnpm
bun run dev
```

## Before you open a pull request

```bash
bun run healthcheck
```

That is exactly what CI runs — formatting, lint, types, the test suite and a
production build — so a green run locally is a green run on the PR. It does not stop
at the first failure, so one pass tells you everything that needs fixing.

Individual pieces, if you want a tighter loop:

| | |
|---|---|
| `bun run format` | Rewrite files with Prettier |
| `bun run format:check` | Check formatting without writing |
| `bun run lint` | ESLint |
| `bun run typecheck` | `tsc -b`, both TypeScript projects |
| `bun run test` | Vitest, once |
| `bun run test:watch` | Vitest, watching |
| `bun run build` | Type-check and bundle for production |

## Things worth knowing before you change the solver

`src/lib/treb/` is the physics and it is the part to be careful with. Read
[`CLAUDE.md`](./CLAUDE.md) first — it is the architecture document for this repo and
explains the decisions that are easy to undo by accident. The short version:

- **Kinematics are data, not derivations.** Every point on every machine is a list of
  terms, so Jacobians and Hessians come out analytically and the energy audit closes
  to ~1e-9. Adding a machine type means adding a term list, not deriving equations of
  motion. Please don't replace this with finite differences.
- **Liftoff is not a threshold.** The projectile is held to the trough by a holonomic
  constraint, and the Lagrange multiplier *is* the normal force. Liftoff is where it
  passes through zero.
- **The machine throws toward +x.** Mirroring a sign convention is silent and
  expensive — the machine still throws perfectly, just backwards. There is a test for
  exactly this.
- **`physics.test.ts` is validation, not a snapshot.** It checks the solver against a
  published instrumented machine ([arXiv:2502.19442]) and against emergent behaviour:
  efficiency peaks at a 100 : 1 weight ratio, the vacuum optimum is 45°. If a change
  breaks one of those, the change is probably wrong rather than the test.

## Style

Prettier owns formatting, so don't spend time on it. What Prettier can't do is the
part that matters here: **comments explain why, and specifically why the obvious
thing doesn't work.** Constraints, failure modes and rejected approaches get written
down; comments that restate the code do not. Match the density and idiom of the file
you are in.

`src/components/ui/` is vendored from the shadcn registry and is regenerated by
`shadcn add` — treat those files as generated, and replace a component locally rather
than editing it in place if it blocks something.
